# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Nebula Finterest (renamed from Finterest in v0.1.35) is a local, offline Electron desktop app that helps a single user visualize their monthly budget more clearly than with a simple calculator. It is explicitly **not** a fintech/investment app: no network calls, no market data, no bank connections. The renderer UI is in French; displayed amounts use EUR formatting.

## Commands

```bash
npm install                # install dependencies
npm run dev                 # run Vite + watched Electron rebuild + Electron shell together
npm run build                # build renderer (vite) then electron main/preload (tsup)
npm run typecheck           # tsc --noEmit
npm run lint                 # eslint over src/**/*.{ts,tsx} and tests/**/*.{ts,tsx}
npm test                     # jest (ts-jest, jsdom environment)
npx jest src/shared/budget.test.ts   # run a single test file
npm run dist                 # full production build + electron-builder (current OS)
npm run dist:win / dist:mac / dist:linux   # platform-specific installers, output to install/<platform>/
```

There is no `test:watch` script; pass Jest CLI flags directly (e.g. `npx jest --watch`) if needed.

## Architecture

Three-layer split enforced by TS path aliases (`@shared`, `@renderer`, `@electron`) and mirrored in both `tsconfig.json` and `vite.config.ts` / `jest.config.ts`:

- **`src/electron/`** — Electron main process. `main.ts` creates the `BrowserWindow` and registers all `ipcMain.handle` routes (`account:*`, `budget:*`). `preload.ts` exposes a single `window.finterest` bridge via `contextBridge` (context isolation on, node integration off) — this is the *only* surface the renderer can call into the main process through. `main.ts` also pins `userData` to `%APPDATA%\Finterest` so the v0.1.35 product rename did not orphan existing accounts. `accounts.ts` (`AccountManager`) manages multiple local accounts: each account is a scrypt-hashed PIN record in `accounts.json`, with its own separate SQLite file (`finterest-<accountId>.sqlite`) and its own `BudgetStore` instance. `store.ts` (`BudgetStore`) owns one account's data using `sql.js` (SQLite compiled to WASM, not a native binding) — every mutation runs in an explicit `BEGIN IMMEDIATE`/`COMMIT`/`ROLLBACK` transaction and then serializes the whole DB back to disk via `persist()` (`database.export()` → `writeFileAtomic` in `fsutil.ts`, serialized through a promise chain). There is no incremental/streaming persistence — every write rewrites the full file. `sync.ts` (`SyncManager`) **copies** every profile (database, avatar, an `accounts-sync.json` manifest) into an optional user-chosen folder. Since v0.1.37 it is one-way: the local profiles (userData, with their PIN records) are the reference, read first, and are never replaced from the folder; profiles found there that this computer lacks are only offered (`listRestorable`) and added on the user's request (`restoreFromCopy`, never over a local file); deleting a profile keeps its copy. Copy errors are recorded in its status and must never fail a local save. `backups.ts` handles the root backup folder `Documents\Nebula Finterest` (timestamped export names, rotation of the uninstall backup, latest backup, summaries); `--import-backup=<file>` and "latest backup after creating a profile" both go through a pending import the renderer confirms. `nebula.ts` is the optional Nebula Hub integration (`@nebula/link` SDK, manifest `nebula.app.json` shipped in `resources\` via extraResources): private widget `finterest.budget.remaining` (only while a real profile is unlocked), private "charge due tomorrow" notifications (once per charge and day), Nebula appearance forwarded to the renderer, intents (`/month?date=`), updates left to the Hub on the user's choice, and the Hub mode (`nebula.hub.dock`: the window is recreated frameless at the Hub's bounds, released on `released`, on Hub loss or on "Detach"). `NEBULA_LINK_SESSION_FILE` points a manual test at a test-mode Hub (Nebula Hub's `tests/link-harness/e2e-app.ts`). `main.ts` honours `FINTEREST_USER_DATA_DIR` to run against a throwaway data folder (use it for any manual testing), holds a single-instance lock, and the renderer runs sandboxed with a build-time CSP (`vite.config.ts`).
- **`src/shared/`** — Pure, framework-free modules used by both the main process and the renderer. `budget.ts` centralizes all budget math (`computeBudgetSummary`, `getCalendarEntries`), input parsing (`parseAmount` accepts French "12,50"), and validation/sanitization (`sanitize*`, `normalizeSnapshot`, `extractBackupSnapshot` which accepts every backup shape ever released) — this is the module to extend for any new calculation or data-shape rule. `sync.ts` holds the pure sync decisions (`decideFileSync`, `mergeAccountRecords`). `budgets.ts` (v0.1.41) holds the budgets / sub-envelopes / pots rules (inheritance from the root budget, monthly vs dated vs open periods, forecast budgets kept out of the "reste à vivre", `amountTone` for green/red amounts); a budget's expenses are ordinary `variable_expenses` rows carrying an optional `budgetId`. Both have test files; main-process tests live in `tests/electron/` (Node environment, `electron` mocked to a temp `userData`). `types.ts` and `accounts.ts` define the shared data contracts (`BudgetSnapshot`, `FixedExpense`, `VariableExpense`, `BackupFile`, `AccountBackup`, etc.) that flow across the IPC boundary.
- **`src/renderer/`** — React UI. `App.tsx` is a single top-level component covering account selection/login, the budgeting dashboard, and settings, inside the family shell (v0.1.38, after Nebula Hub's renderer): a frameless window with a 36 px `.titlebar-drag` strip and Windows controls tinted through `setWindowTheme` (IPC `app:setWindowTheme`, theme name validated against a table in `main.ts`), `components/Sidebar.tsx` (floating panel, groups "Mon budget" / "Outils", profile card, Nebula Hub status card, footer; icon rail below 1100 px, top bar below 720 px), a centered `.workspace-inner` column (1480 → 2280 px), `components/Dialog.tsx` (focus-trapped confirmations) and `components/ScreenState.tsx` (empty states). Navigation views include `calculator` (no more simple/advanced mode switch). `components/Icon.tsx` is a verbatim port of `@nebula/design` — never edit glyphs there; reuse names from the set. `styles.css` holds six variable-driven palettes selected by `data-theme` on `<html>`: `nebula-dark` (the default, also on bare `:root`), `nebula-light`, the translucent `glass-dark`/`glass-light` (backdrop-filter surfaces), and the frozen legacy `old-dark`/`old-light`; `theme.ts` owns the choice and resolves `system` to the Nebula pair. `appearance.ts` layers per-machine preferences on top (accent colors written as inline CSS variables on `<html>` — never on `old-*` —, `data-background`, `data-motion`, sound settings), `sound.ts` synthesizes UI sounds with Web Audio, `effects.ts` attaches the document-level click sound/ripple and glass highlight, `components/BackgroundFx.tsx` renders the animated backgrounds, and `components/Icon.tsx` is the app's own SVG icon set (use it instead of Unicode glyphs). No component library or router is used.

### Data flow

Renderer → `window.finterest.<method>()` (preload) → `ipcMain.handle` (main.ts) → `AccountManager` → active account's `BudgetStore` → sql.js DB → `persist()` to `finterest-<accountId>.sqlite` in Electron's `userData` path. Every mutating `BudgetStore` method returns the fresh `BudgetSnapshot`, so the renderer re-syncs state directly from each IPC call's return value rather than maintaining independent derived state.

### Backup/import

Export produces a single JSON `BackupFile`/`AccountBackup` (app name + version + ISO timestamp + full snapshot) written via a native save dialog; import reads a JSON file via a native open dialog, runs it through `validateBackupFile`, and replaces the active account's tables inside one transaction. A full account export currently contains only the active account — other local accounts on the same machine are not included in that file.

### Security posture (current, not final)

Local accounts use salted scrypt for PIN verification (`accounts.ts`) — this protects in-app access only. Database-at-rest encryption and full account recreation on import are explicitly noted as pending work (see `README.md`).

## Repo-specific conventions

- **Nebula Hub is optional**: the app must keep working without it (the SDK never throws or blocks when the Hub is absent). Never share anything while no real profile is unlocked; never add a capability without declaring it in `nebula.app.json` (the Hub refuses undeclared ones). Running a manual test with `FINTEREST_USER_DATA_DIR` also isolates the backup folder.
- **Auto-update compatibility**: installs update themselves over existing data. Schema changes must be additive migrations in `BudgetStore.migrateSchema`, new `accounts.json` fields optional, and the backup format stays `version: 1`-readable; extend the legacy fixtures in the tests when touching any of these.
- **Mandatory documentation updates**: `.github/copilot-instructions.md` and repo convention require that non-trivial changes update `README.md` (project overview, user guide, and light technical reference — this is what GitHub renders as the repo's landing page; there is no separate README.txt), `DEV_CHANGES.md` (new dated section at the top, technical/developer detail), and, up to v0.1.35, `PATCH_NOTES.md`. Since v0.1.36 the user wants the patch notes **only in the GitHub release body**, so do not add new sections to `PATCH_NOTES.md` — check the other files' existing structure before adding to them.
- **Family shell**: the shell (sidebar, content column, states, dialogs) is ported from Nebula Hub's renderer at the commit named in the `styles.css` / component headers; keep every sidebar selector scoped to `.sidebar` and check that entries stay ≥ 44 px in the running app. One gradient (primary) button per screen; only `opacity` / `transform` keyframes; the background is the only infinite animation.
- **Styling work**: the renderer follows the shared **Nebula** design language (palette, blue→violet accent gradient, ambient `.bg-glow`, motion scale) — its canonical source is the sibling project's `Nebula/src/nebula/web/static/css/theme.css`, summarized for agents in `NEBULA_DESIGN.md` (deliberately gitignored, shared out of band). Keep the `old-dark`/`old-light` blocks intact: they are the previous emerald/gold themes, still user-selectable and intentionally frozen. Keep IPC behavior and budget semantics untouched, define repeated colors/spacing as CSS variables, and validate with `npm run typecheck` / `npm run lint` / `npm run build` after changes. `.github/agents/finterest-styling.agent.md` predates the Nebula rework — its process guidance still applies, its palette guidance does not.
- **Electron kept external**: the main-process bundle (tsup) marks `electron` external so packaged builds use Electron's built-in runtime instead of bundling it.
- Windows builds set `CSC_IDENTITY_AUTO_DISCOVERY=false` (unsigned code signing disabled) automatically via `npm run dist`; `.github/workflows/build-installers.yml` builds Windows/macOS/Linux artifacts on their native runners.
